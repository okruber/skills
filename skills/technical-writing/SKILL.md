# Technical writing — plain, unambiguous prose

## When this applies

Any content a human reads as instruction or explanation, in a file or in a chat
reply: READMEs, runbooks, setup and troubleshooting guides, PR descriptions,
issue reports, release notes, API or architecture docs and explanations, and
any time you give step-by-step instructions.

## When this does not apply

Casual back-and-forth, brainstorming, exploratory discussion, commit messages,
and prose in Obsidian vault notes. Keep those conversational. The no-em-dash
rule and the code-comment rules still hold there.

## Rules

Write in the style of ASD-STE100 Simplified Technical English.

- One instruction per sentence. For procedures, use the imperative ("Run the
  migration."). Put any condition before the command ("If the build fails, read
  the log.").
- Keep instruction sentences under about 20 words. Keep explanation sentences
  under 25. Split anything longer.
- Use active voice. Use simple tenses only. No "has been", no "is being", no
  present perfect.
- Do not hedge with should, would, may, might, or could. Write "must" for a
  requirement, "can" for a possibility, or state the thing as fact.
- One term per concept, used consistently through a document or reply. Pick
  "config" or "settings" and stay with it.
- Delete filler rather than replacing it: leverage, utilize, seamlessly, robust,
  comprehensive, in order to, it's worth noting that. Write "use" for
  leverage and utilize. Write "to" for "in order to".
- Keep articles and "that". This is short, not terse. Do not strip words to save
  length.

## Check before you send

Read the draft once and ask three questions. Does any sentence carry two
instructions? Does any sentence hedge? Does any concept have two names? Fix what
you find, then send.
